How to actually use this.

Setup, the daily loop, the six commands that carry most of the weight, and what to do when something blocks you. If you've used Claude Code before, you already know 90% of the mechanics — the framework changes what happens after you write code, not how you write it.

01 — Orientation

What you're installing, in plain terms.

It is not a library, a CLI, or a service. It is a directory of instructions that Claude Code reads — agent definitions, slash commands, rules, hooks — plus a handful of Python scripts that record what happened and enforce the gates.

You get a team

Twelve specialist agents — security, architecture, QA, UX, performance, docs, education and more — coordinated by a facilitator that decides who is needed for a given change and synthesises what they find.

You get gates

A quality gate wired into a pre-commit hook, a review-existence check, a secret scanner, file locks for parallel agents, and a main-branch push blocker. They run whether you remember them or not.

You get a memory

Every review and planning session is captured to an immutable log, indexed into SQLite, and — with your approval — promoted into curated memory that future sessions read before building.

You keep your workflow

Your editor, your language, your git flow. Python is only needed for the framework's own scripts — the projects running it are Dart and Python respectively.

Two places you'll be typing

Throughout this guide, shell blocks are your normal terminal. Claude Code blocks are typed at the Claude Code prompt after you run claude in your project folder. Slash commands only work in the second one.

02 — Setup

From nothing to your first command.

shell
# 1 — clone and isolate
git clone https://github.com/Diviner-Dojo/agent_framework_template
cd agent_framework_template
python -m venv .venv
# macOS/Linux: source .venv/bin/activate
# Windows: .venv\Scripts\activate
 
# 2 — install and initialise
pip install -r requirements.txt
cp .env.example .env # optional (phone push)
python scripts/init_db.py
 
# 3 — verify
pytest tests/ -v
Claude Code
# 4 — launch in this folder, sign in, then:
/deliberate "what should I build first here?"

Prerequisites

required Python 3.11+ and Git.

required Claude Code — the CLI that runs the agents and slash commands.

required A paid Anthropic plan (Pro or Max). The agents will not run without it. Run claude once and sign in.

optional VS Code, and the GitHub CLI for /discover-projects and /ship.

Then make it yours

Open CLAUDE.md and fill in Project Identity, your stack, and any Domain Safety Constraints. This file is the project constitution — it loads on every turn. Keep it lean; detail belongs in path-scoped rules and on-demand skills.

Three ways in — pick one

A

Try it in the template

Just clone, as above. You get the framework itself — agents, commands, hooks, capture pipeline — and no application code; this is infrastructure, not a starter app. Good for reading the agent definitions and running your first /review against the framework's own scripts.

B

Start a new project

Run /spawn-project inside Claude Code. It scaffolds a fresh project from the template in its own folder, then /seed bootstraps its structures and first discussion.

C

Adopt an existing codebase

Don't clone. Run /apply-framework. It assesses value and risk first, surfaces collisions, and only deploys onto a back-out branch once you say go.

After path C, /onboard runs the deeper takeover — maps the codebase, reverse-engineers ADRs for decisions already made, calibrates standards to what you actually do, and builds a stabilisation plan and debt ledger.

03 — The daily loop

The rhythm you'll be in most days.

Write code→ /review→ Fix blocking findings→ Quality gate→ Commit
Change sizeRequired sequence
Micro-fix
cosmetic only		 Change → lint → verify visually. Skips /plan and /build_module, not the quality gate. If it touches data flow, lifecycle, schemas, or platform channels it is not a micro-fix.
Small
1–2 files		 Implement → quality gate → /review → commit. Skip /review only for docs- or config-only changes.
Multi-file
3+ files, or 2+ new modules		 /plan → /build_module → quality gate → /review → fix blocking findings → commit.

The rule that catches everyone once

If you are about to commit code without having run /review, stop and run it. The gate will block you anyway — the review-existence check fails when code is staged and no review report from today exists. There is no deadline that justifies skipping independent evaluation; that's Principle #4, and it's the whole point.

04 — Core command

/review — the one you'll run most.

Assesses risk, assembles the right specialists, verifies their claims, and writes a structured report with a verdict.

Claude Code
# specific files
/review src/routes.py src/models.py
 
# or let it auto-detect scope:
# PR diff → staged → unstaged → HEAD~1
/review
 
# cheaper / deeper / commented on the PR
/review --cost low
/review --deep # + git history analyst
/review --comment # post to the PR

Reading the verdict

approve ship it.

approve-with-changes ship, but the advisories are owed.

request-changes blocking findings must be fixed first.

reject the approach itself is wrong — go back to /plan.

Risk decides the panel size

RiskAgentsMode
Low2–3Ensemble
Medium3–4Structured dialogue
High4–5Dialectic / adversarial
Critical5–6Full adversarial panel

Default to the smaller panel. A five-agent review on a config change is pure cost — the risk tiers exist so you don't pay it.

Two things that make findings trustworthy

Verification. The facilitator re-reads the actual code at every reported location before accepting a claim — hallucinated line numbers get caught here.

No suppression. Low-confidence findings are grouped into a "Speculative" section rather than dropped. You decide what's noise; the framework doesn't decide for you.

Advisories don't disappear

Non-blocking findings are carried forward into the next review as open advisories until resolved or formally accepted. An advisory seen in three independent reviews escalates to blocking — the Rule of Three. That's how "we'll fix it later" stops being permanent.

05 — Core commands

/plan then /build_module — for anything substantial.

Design gets reviewed before code exists, because catching a wrong shape after implementation costs an order of magnitude more.

/plan — spec first

1. A confidence check. If intent or scope is under ~95% clear, it asks rather than guesses.

2. Prior-art lookup — greps solution paths, known-broken approaches, ADRs and promoted patterns before proposing anything.

3. A structured spec with requirements and acceptance criteria.

4. Specialist design review of the spec.

5. Your approval. Nothing is built until you give it.

/build_module — build with checkpoints

Implements task by task. After each task, the facilitator checks it against trigger categories — new module, architecture choice, schema change, security-relevant code, external API, user-facing flow.

On a trigger, exactly two specialists review that task and answer APPROVE or REVISE in under 200 words.

Hard cap of two rounds. Unresolved concerns are flagged unresolved-checkpoint and surfaced in the build summary — never silently dropped, never allowed to stall the build.

Why checkpoints, not just a final review

A review at the end finds problems when they're expensive. A checkpoint after the task that chose the abstraction finds the same problem when it costs ten minutes. Two specialists, 200 words, two rounds maximum — small enough that you'll actually leave it on.

06 — Core command

/deliberate — when you don't know what to build.

A structured multi-agent discussion on any question. Use it before /plan, when you're stuck between two designs, or when you want the argument itself preserved.

Claude Code
/deliberate "should batch processing be Celery or an in-process pool?"
mode: dialectic synthesis · intensity: high
→ architecture-consultant, performance-analyst, independent-perspective
 
thesis in-process pool — no broker, no ops surface
antithesis Celery — retries and visibility are the actual requirement
synthesis Celery, but the queue is an interface so it can be swapped
 
captured → discussions/…/transcript.md · candidate ADR flagged

Also useful for

Post-mortems, "is this worth building?", disagreeing with an earlier decision, and prising apart a requirement you only half understand.

Two grilling modes

grill-me interviews you, one question at a time with a recommended answer, until every branch is resolved. grill-yourself inverts it — the model writes the hard questions on your behalf and answers each with a recommendation, so your job shrinks to verdicts.

Everything is captured

The full transcript, every dissent, and the synthesis are sealed into a discussion you can grep months later — which is the point.

07 — Advanced

/goal-loop — iterate until a goal is provably met.

For work that is genuinely loop-shaped: it has a verifiable done-state, you expect build → verify → refine convergence, and it isn't a micro-fix.

The separation that makes it safe

Control flow lives in scripts/goal_loop.py — a deterministic driver that owns ticks, budget, the termination ladder, and re-verification. The model is invoked only to build a delta, to judge a criterion, or to phrase a gate. The agent that builds is never the agent that judges.

It is suggested, never imposed

It never auto-starts. A goal that's subjective, exploratory, or only verifiable through a prohibited action is routed to grill-me, /plan, or /deliberate instead — the contract-authoring skill gatekeeps that first. On completion it halts for /review plus a required education walkthrough. It never pushes and never auto-merges.

Start with authoring-goal-contracts, which interviews you into a valid contract with at least one deterministic anchor. ADR-0026 / ADR-0028.

08 — Troubleshooting

What do I do when…

…the quality gate blocks my commit

Read which check failed — the output names it. Run python scripts/quality_gate.py --fix to auto-remediate formatting and lint. For a legitimate skip, use the matching --skip-* flag and put a one-line justification in the commit message (skip-tests: docs-only change). One project's retro found 85 unexplained coverage skips; the justification requirement is what made that visible.

Full recovery paths for all eight failure classes: the recovering-from-failures skill.

…a hook blocks my edit

Three reasons, in order of likelihood. File lock — another agent is editing it; locks expire after 120 seconds. Secret detected — the content matched one of twelve secret patterns; move it to .env. Protected file — .env, .git/, the metrics DB, and settings.json are agent-immutable by design. You edit those by hand; that's the point.

…the review found something I disagree with

Say so, with reasoning. The verdict is advice, not a court order — you are the human gate. What you shouldn't do is silently ignore it: record the disagreement, because a declined advisory needs a one-sentence rationale to stop the knowledge being lost. If you're right and the pattern recurs, that's evidence the specialist's calibration needs adjusting, and scripts/audit_calibration.py is how that gets surfaced.

…the same fix isn't working after two attempts

Stop writing code. Two failed attempts means your mental model is wrong, and no amount of coding fixes a wrong mental model — only evidence does. Add logging at every step of the pipeline, run it, read the actual runtime sequence, then diagnose. This two-strike rule exists because a project burned six deploys treating an architectural problem as cosmetic.

…I'm not sure what to build, or the request is ambiguous

That's Principle #9 territory — clarify to ≥95% confidence on intent and scope before acting. Use grill-me to be interviewed one question at a time, or /deliberate to get the specialists arguing about it. Both checkpoint to disk, so an interrupted session resumes where it stopped.

…my context is running out mid-task

The session self-monitors context occupancy and nudges at a model-specific threshold. Run /handoff (or let the wrapping-up-sessions skill fire): it checkpoints state, writes docs/handoff/HANDOFF-<timestamp>.md, and points to it from BUILD_STATUS.md. Paste that into a fresh session and continue. Wrap-up never pushes, never auto-merges, and never launches a continuation without explicit consent.

…I'm about to build something that might already exist

Grep first — the searching-prior-art skill is a checklist for exactly this. Check the regression ledger's Known-Broken Approaches, solution paths in memory/projects/_self.md, existing ADRs, and promoted patterns. Zero results is a normal outcome for novel work; the point is that two minutes of grep beats two hours of rediscovery.

09 — Autonomy

Working while you're away.

It can reach your phone

Set NTFY_TOPIC in .env and long-running work sends push notifications via ntfy.sh. Two-way: an agent can ask a gating question and wait for your one-tap answer, then keep going.

Replies are treated as untrusted — validated against a fixed allow-list, and the framework acts on the matched choice label, never the raw text. The topic slug is the only authentication, so it lives in .env and is never printed.

Autonomy is scoped in writing

The Autonomous Execution Authorization block in CLAUDE.md names the branch scope, the effective date, the authorized actions, and — critically — the prohibited ones.

The shipped defaults prohibit pushing to any remote, destructive git, editing settings.json, and auto-merging. Full workflow without permission prompts; never a skipped step.

10 — Evolution

Changing the framework itself.

You are expected to. There's just a path, so improvements are evidence-driven rather than vibes-driven.

Pattern across reviews→ Proposal with evidence→ Steward gate→ Your approval→ /review→ Doc sync

A pattern, not an incident

One bad review isn't evidence. The trigger is the same problem appearing across several — which is what the metrics layer exists to make visible.

The steward judges fit

Verdicts are APPROVE / REVISE / DEFER / DECLINE, measured against PHILOSOPHY.md. It's the one agent that can decline a change on principle rather than on correctness.

Smallest change that works

Principle #8: prompt before command, command before agent definition, agent definition before architecture. Escalate only when the cheaper intervention has demonstrably failed.

13 — Practice

Five habits that decide whether this works for you.

01

Right-size the panel

Default to two agents. Reserve the full panel for security, architecture, data migration, and anything with a silent failure mode. A five-agent review on every change is the fastest way to resent the framework.

02

Keep CLAUDE.md lean

It loads on every turn, so every line costs. Detail belongs in path-scoped rules and on-demand skills. When a review comment says "you didn't know X" — that's the signal the constitution needs one more line, not ten.

03

Write the ledger entry while it hurts

Right after a fix, when the root cause is still vivid. Name the root-cause class, not just the symptom — that's what makes the second occurrence get diagnosed instead of rediscovered.

04

Take the education gate seriously

It's the easiest thing to defer and the most expensive to skip. Code you can't explain is code you can't debug at 2am, and the framework can't help you then.

05

Run /retro at milestones

Not every phase — it's expensive. Batch a few sprints. Its job is to find the pattern you're too close to see, and patterns need a few data points.

06

Let it argue with you

The value isn't a compliant assistant. It's a specialist that says "this replaces a proven capability with an unproven one — what's the rollback plan?" and means it. If every review approves cleanly, your panel is too small or your risk tiers are wrong.
