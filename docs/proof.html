02 — Case study

A licence-verification platform where a wrong answer is the product failing.

Python 3.11 · FastAPI Playwright Celery + Redis 51 states 62 state configs

VerificationPortal

Automates professional licence verification across U.S. state portals — browser scraping, bulk datasets, and public APIs, cascading per state. The domain has a nasty property: a confidently wrong answer is worse than no answer. Reporting an expired contractor licence as valid is a compliance failure that looks exactly like success.

Exhibit A — six defects, zero blast radius

An adversarial panel took apart a scorer before it wrote a single value.

A new endpoint-scoring module — a gated lexicographic ranking function that decides which data source each state should trust — was built and looked fine. Four independent reviewers were dispatched against it with instructions to refute, then a synthesis pass. The verdict was blunt: "NOT CORRECT AS-IS." Six distinct real defects plus two test gaps, all found pre-activation.

memory/bugs/regression-ledger.md — "Endpoint scorer: 6 correctness defects caught by adversarial review before activation (ADR-0038)"
M1 (load-bearing) _build_composite_plan spliced REFERENT-FAILED endpoints — re-opening the exact hole the referent gate exists to close. M2 unbounded CapabilityVector inflated the composite past 100 + gamed the gate. M3 _composite_display's round(...,2) erased the freshness + tiebreak tiers, so the stored composite disagreed with rank_state's order. M4 rank_state winner was input-order-dependent on ties — breaks idempotence. M5 a plan could name a find_source with zero find capability. M6 find/status exclusion used source_id equality, dropping a distinct deep endpoint. M-RISK-2 classify_delta returned "degradation" without drift attribution — a harness change could masquerade as portal rot. Known-Broken Approach recorded: shipping a scoring/ranking function on design-review and happy-path tests alone.

Every one of the six now has a named guard test — test_ranking_is_deterministic_across_input_permutations, test_composite_is_order_preserving_function_of_rank_key, and four siblings. The interesting part is not that a review found bugs. It is that M3 and M4 are invisible to a happy-path test suite: both produce plausible output every single run. A ranking that silently depends on input order does not crash. It just quietly gives a different answer on Tuesday.

Exhibit B — the word "Verified" meant nothing

An audit found expired licences being reported as Active.

1
A substring match with no negation guard
parser._normalize_status matched "active" inside "Not Active - Expired". Expired licences read as Active — and the string is real portal output, not a hypothetical.
2
"Verified" rows with no evidence behind them
The bulk path wrote no per-row artifact, so rows were mislabelled provenance "cache" — reporting reuse of a cached result that never existed. Separately, rows were being marked Verified with no expiration date at all.
3
The definition was rewritten, not patched
ADR-0020 redefined the gate: a row cannot be LicenseVerified unless it has a loadable evidence record AND an expiration date. Everything else demotes to NeedsReview with a reason code.
4
The cost was accepted openly
Roughly 700 previously-"Verified" rows reclassified to NeedsReview. That is the framework working: the number went down because the number had been lying.

What made it durable

The fix did not stop at code. It became .claude/rules/verified_gate_and_provenance.md — a rule loaded into every future session — including the specific requirement that "no artifact" must never be labelled "cache", and a test that fails if any report surface re-derives status from the lossy legacy field instead of the persisted canonical one. A future agent cannot reintroduce this by accident without tripping a test written by the agent that found it.

Exhibit C — a 403 that wasn't

Two states nearly got silently dropped because "Forbidden" looked like an answer.

The Texas and Arizona bulk sources both returned 403 Forbidden and read as offline. Accepting that would have quietly removed two states from coverage — the failure mode the project fears most, because nothing looks broken. Investigation at the source found the portals were TLS-fingerprinting the HTTP client and rejecting it at the handshake. A different client downloaded the full sanctioned CSV immediately: Arizona, 9.16 MB, 43,886 records.

.claude/rules/endpoint_integrity.md — elevated to Principle #10 by developer directive, 2026-06-26
"We must never let batches be run through endpoints that we are not certain are open and effective. Never, never, never accept a stale endpoint in its own right without trying and raising and yelling very loudly that we cannot pass additional records through it." Four non-negotiables: never silently accept a degraded endpoint · when you cannot repair it, yell loudly · never run a batch through an endpoint you are not certain of · keep endpoint state visible in a dashboard. The bright line: repair via sanctioned means only. A TLS-impersonating transport for a public CSV is fine. Solving a CAPTCHA is not — that is a blocked endpoint, and the honest move is to say so.

This is the framework's evolution path running end to end: an incident produced a developer directive, the directive became a rule file, the rule became a numbered principle in the project constitution, and the principle now constrains every future session — with an explicit ethical boundary attached so "be creative about access" can't drift into "bypass whatever's in the way."

03 — Case study

A Flutter app where the wrong microcopy is a clinical failure.

Flutter · Dart Riverpod · drift Supabase 443 source files 511 test files

Insight Journal

An ADHD-informed journalling app with voice capture, on-device storage, and AI-assisted reflection. The domain constraint is unusual and absolute: the app must never mention missed days, gaps, or absence — not even implicitly. No streaks. No gap-shaming calendars. A feature that quietly violates this is a clinical failure, not a UX nitpick.

Exhibit A — the two-PR pattern

One untested default broke every speech engine at once.

A new speech-to-text service was added and made the production default in the same commit. It had never been tested on a physical device. Its WebSocket auth failures triggered a latent microphone resource leak, which then blocked all three speech engines from acquiring the OS microphone. Voice mode — the core of "effortless capture" — was dead for multiple sessions, and it was only visible on real hardware.

.claude/rules/capability_protection.md — the Capability Protection Protocol (ADR-0035)
You cannot change a provider default in the same PR that introduces the new implementation. This is the Two-PR Pattern. It is not negotiable. PR N add the implementation. The proven default stays. Register the capability as EXPERIMENTAL. PR N+1 after confirmed device testing, change the default. Mark it PROVEN, and cite the device, OS version, and date. The pause between "I built this" and "this is now the default" is where device testing, review, and the registry update happen.

Three enforcement points followed. The quality gate now hard-blocks a commit that promotes an EXPERIMENTAL capability to default — upgraded from a warning, because the warning had not been enough. Any diff touching a provider default automatically adds the independent-perspective agent to the review panel and asks it one question: "does this replace a proven capability with an unproven one, and what is the rollback plan?" And a capability marked PROVEN more than 30 days ago is treated as unconfirmed until re-tested — because verified state gets assumed far faster than it gets re-checked.

Exhibit B — the silent overwrite

A parallel agent quietly reverted a 681-line redesign.

A feature was built in a git worktree that had branched before a major UI overhaul landed. On merge, git did what git does: the older version of a shared file won, and a 681-line rewrite was silently replaced. Nothing failed. Nothing warned. It surfaced during unrelated testing days later.

The resulting rule is short and specific, which is why it works: diff the worktree branch against its base before merging, manually review any file changed on both sides, stop and escalate at 50+ lines of change on both sides, and never auto-merge a worktree branch touching UI files. As the rule puts it: worktree agents cannot see changes made after they branched, which makes them structurally prone to overwriting concurrent work. Parallel agents are a real capability with a real failure mode, and the honest response is a guardrail, not enthusiasm.

Exhibit C — the ledger recognising a repeat

The second sighting of a bug class was diagnosed by name.

Course generation started failing with a truncation error on a large repository. Adding API credits did nothing — it was never billing. The root cause: a hard output-token cap sized for an older, lighter payload, left unchanged when the payload grew.

memory/bugs/regression-ledger.md — root-cause class field
Root cause class: abstraction narrowing (output cap under-sized for its payload — 2nd sighting; the sibling chapter call hit the identical failure first). The sibling constant had already hit this exact stop_reason and been raised 2800 → 8000. The digest constant was simply never re-sized for its heavier payload. Fix: sized to MATCH the sibling rather than an intermediate value — architecture review showed an intermediate cap risks a second truncation round-trip.

This is the part that only pays off after months of discipline. The ledger does not just record what broke — it records the root-cause class. So the second occurrence arrives pre-diagnosed, the fix is sized against the first one instead of guessed at, and the review can ask the better question: where else does this class live?

04 — The mechanism

Every one of those incidents took the same route.

This is what "self-improving" means here. Not an agent editing its own prompt — a human-gated pipeline that converts a specific failure into a constraint that loads on every future turn.

Incident→ Captured discussion→ Root-cause class→ Guard test→ Rule or ADR→ Loaded every session

Nothing rests on memory

The constraint lives in a rule file the agent loads, a test the gate runs, or a hook that blocks the write. Not in a retro nobody rereads.

Three sightings promote

A finding seen in three independent contexts is surfaced by the Rule of Three as a promotion candidate — and an advisory that recurs three times escalates to blocking.

A person signs every promotion

Nothing reaches curated memory or tightens a classifier without human approval. The framework proposes; it never self-legislates.

05 — The other side

What it costs, and what it does not fix.

A page of wins is marketing. Here is the honest ledger — most of it drawn from the projects' own retrospectives, where the framework's overhead was measured and then cut.

It is not free, in tokens or time

A five-agent panel on every change is genuinely wasteful, and both projects learned that the hard way. The verification platform now runs a default execution profile: two-agent ensembles for low and medium risk, the full panel reserved for security, architecture, and data migration; workers on the cheaper tier; reflections only after a REVISE on a medium-or-higher change. Its own estimate — roughly a third of full-panel cost at comparable quality.

Ceremony erodes under deadline

One retrospective found 85 coverage skips and 51 test skips with no recorded justification — discipline quietly draining away, invisible until someone queried the gate log. The response was not exhortation. Skips now require a one-line justification in the commit message, which makes them auditable in git history.

Gates have real holes

Review-existence checks that a review from today exists, not that it covered your staged files. The pre-commit hook can't pass --skip-reviews through. A 5-minute verification cache can silently suppress the regression-ledger reminder. All three are documented in the constitution rather than left for you to discover.

It cannot see what it cannot run

The microphone leak was invisible to every static review and every widget test — it needed physical hardware. So the rule that came out of it mandates device verification, not more review. Knowing which failures a review panel structurally cannot catch is part of using one well.

Where the value actually lands

The pattern across both projects is consistent: the framework earns its cost on changes with silent failure modes — ranking functions, status normalisation, provider defaults, anything where wrong output is indistinguishable from right output until a user is harmed. On a CSS tweak it is pure overhead, which is exactly why the risk tiers exist and why the micro-fix protocol lets small things stay small.

Your turn

The interesting question isn't whether it works. It's what it would catch in your codebase.

The fastest way to find out is to point it at code you already have and read the first review it produces.
